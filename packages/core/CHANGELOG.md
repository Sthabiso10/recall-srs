# @recall-srs/core

## 0.3.0

### Minor Changes

- Upgrade the scheduler to FSRS-6, and fix three places where the FSRS-5
  implementation diverged from the reference.

  Everything here was verified against two independent MIT-licensed reference
  implementations maintained by the algorithm's own authors —
  [ts-fsrs](https://github.com/open-spaced-repetition/ts-fsrs) and
  [py-fsrs](https://github.com/open-spaced-repetition/py-fsrs) — which agree with
  each other. Where this package disagreed, the reference won. A new conformance
  suite runs the scheduler against 244 state transitions generated by ts-fsrs, so
  the two cannot drift again silently.

  ### Correctness fixes

  These change the schedule. Each was a real divergence, not a rounding
  difference.

  - **Post-lapse stability was capped too generously.** It was clamped to the
    pre-lapse stability `S`; the correct cap is `S / e^(w17·w18)`, which is
    strictly lower. A lapse on a weak, badly overdue card could hand back
    essentially all of its stability, rescheduling a card the learner had just
    failed nearly as far out as if they had passed it. Affects roughly 7% of
    states under FSRS-6's weights, and considerably more under FSRS-5's.
  - **A passing same-day grade could shrink stability.** FSRS-6 clamps the
    same-day multiplier to at least 1 for Hard/Good/Easy. Without it, a Hard on
    an already-stable card reduced its stability — the learner recalled the card
    and was penalised for it.
  - **Difficulty mean reversion used a clamped baseline.** The reversion target
    is `D₀(Easy)` _unclamped_. Under FSRS-5's weights that value is ≈ 3.2 and
    clamping it to `[1, 10]` changed nothing, so the bug was invisible; under
    FSRS-6's it is ≈ −4.77, and clamping it to 1 puts the target nearly six
    points too high, drifting every card in the collection harder than it should
    be.

  Also: stability is now clamped to `[0.001, 36500]` rather than floored at 0.01
  with no ceiling. Stability is multiplied on every successful recall, so a
  long-lived card could previously overflow to `Infinity`, after which every
  interval it produced was `NaN` and the card vanished from the schedule. Initial
  stability is separately capped at 100 days.

  ### FSRS-6
  - `FSRS_6_DEFAULT_WEIGHTS` — 21 parameters, and the new default for
    `DEFAULT_FSRS_CONFIG`. FSRS-6 adds `w19` (same-day gains now shrink as a card
    gets stable) and `w20` (the forgetting curve's decay, previously hard-coded
    at 0.5, is now fitted per learner).
  - `retrievability` and `intervalForRetention` take an optional weight vector
    and derive `DECAY`/`FACTOR` from it via the new `decayFactorFor`, so
    `R(S, S) = 0.9` continues to hold exactly for any fitted decay.
  - `migrateWeights` converts stored 17-weight (FSRS-4.5) and 19-weight (FSRS-5)
    vectors to 21. The conversion is the reference's, and is chosen so a migrated
    vector reproduces the schedule it already produced — an existing learner is
    never silently moved onto a different algorithm. Pass old vectors straight
    in; the scheduler and optimiser migrate them.
  - `validateFSRSConfig` now range-checks every weight against
    `FSRS_WEIGHT_BOUNDS` instead of only counting them, and rejects a length that
    belongs to no FSRS version.
  - The optimiser fits all 21 parameters, including the decay, and accepts a
    stored FSRS-5 vector as its starting point.
  - `FSRS_WEIGHT_BOUNDS` is now a single table shared by the validator and the
    optimiser. It used to be duplicated by hand in `optimizer/bounds.ts`, which is
    exactly the arrangement where one copy drifts and nothing notices.

  ### Banded interval fuzz

  `fuzzMode: 'banded'` implements the reference's jitter: the spread widens with
  the interval (±15% of the portion between 2.5 and 7 days, ±10% of 7–20, ±5%
  beyond), intervals under 2.5 days are left alone, and a card is never fuzzed
  earlier than it has already been waiting. The previous flat-percentage scheme
  is still available as `fuzzMode: 'ratio'`, and setting `intervalFuzzRatio`
  without a mode still selects it, so existing configurations are unaffected.
  Fuzz remains off by default.

  ### Migrating

  Most callers need no changes. Intervals will differ, because FSRS-6's weights
  differ from FSRS-5's — that is the upgrade. To keep the previous schedule
  exactly, pass the old weights explicitly:

  ```ts
  import { createFSRSScheduler, FSRS_5_DEFAULT_WEIGHTS } from '@recall-srs/core';

  const scheduler = createFSRSScheduler({ weights: FSRS_5_DEFAULT_WEIGHTS });
  ```

  Stored per-learner weights need no action: they are migrated on use, to values
  that reproduce their current schedule.

  Two things to know at the type level:

  - `FSRSConfig` gained a required `fuzzMode` field. `createFSRSScheduler` takes
    a `Partial<FSRSConfig>` so most callers are unaffected, but code that builds
    a complete `FSRSConfig` literal will need the extra key.
  - Nothing was removed. `FSRS_5_DEFAULT_WEIGHTS`, `FSRS_5_WEIGHT_COUNT`,
    `FSRS_DECAY` and `FSRS_FACTOR` are all still exported and still mean what
    they meant.

- Add a learning ladder for new cards, and share one implementation with the
  relearning ladder.

  FSRS schedules from stability alone, so a brand-new card rated Again was
  scheduled from `w0` — about five hours out. Five hours is the wrong answer to
  "I have never seen this and just got it wrong": the learner is sitting there
  now, the material is in working memory now, and the cheapest correct
  repetition available is a minute from now. Anki and the FSRS reference
  implementation both put a short ladder in front of the long-term curve;
  `@recall-srs/core` only had one for lapses.

  ```ts
  createFSRSScheduler({
    learningStepsMinutes: [1, 10], // new cards — the new default
    relearningStepsMinutes: [10], // cards that lapsed — unchanged
  });
  ```

  Grade semantics are the reference's (`BasicLearningStepsStrategy`), and now
  apply to both ladders:

  | Grade | On a ladder                                                            | On a review card                 |
  | ----- | ---------------------------------------------------------------------- | -------------------------------- |
  | Again | back to the first step                                                 | falls onto the relearning ladder |
  | Hard  | holds position; midpoint of the first two steps, or 1.5× the only step | schedules from the curve         |
  | Good  | advances one step, graduating if there is no next one                  | schedules from the curve         |
  | Easy  | graduates immediately                                                  | schedules from the curve         |

  Study sessions already treated `learning` and `relearning` identically, so
  ladder cards requeue inside the same sitting with no changes needed.

  ### Behaviour changes
  - **A new card graded Good no longer goes straight to `review`.** It moves to
    `learning` with a ten-minute step and graduates on the next Good. Grade Easy
    to graduate in one step, or set `learningStepsMinutes: []` to restore the
    previous behaviour exactly.
  - **Failing a new card is no longer counted as a lapse.** Previously any Again
    incremented `lapses` and sent the card to the relearning ladder, including on
    a card that had never been recalled. A lapse means "you knew it and forgot
    it"; only a card in `review` can lapse now. This was inflating lapse counts
    and tripping the leech threshold on cards nobody had learned yet.
  - **`Hard` and `Easy` now mean different things on the relearning ladder.**
    Every passing grade used to advance exactly one step. Hard now holds
    position and Easy graduates outright, matching the reference.
  - **A lapse with no relearning steps configured now lands in `review`, not
    `learning`.** It was already being given a curve interval; the status was
    simply inconsistent with it.
  - `repetitions` counts reviews on the long-term curve, so it no longer
    increments for a grade that only moves a card along a ladder.

  ### Also
  - `learningStepsMinutes` is validated like `relearningStepsMinutes`: every step
    must be a positive number of minutes.
  - The ladder logic lives in `algorithm/steps.ts` as `resolveStep`, one function
    serving both ladders, rather than being inlined twice in the scheduler.

## 0.2.1

### Patch Changes

- Localise the default components.

  The engine was always language-agnostic — `question` and `answer` are opaque strings the
  scheduler never reads — but the components shipped hardcoded English, so translating the UI
  meant abandoning them for a render prop.

  - `<RecallIntl locale strings>` sets language and number formatting for the whole tree.
    `strings` is a deep partial, so overriding three keys leaves the rest English rather than
    blank.
  - `<StudyView>` gains `revealLabel`, `skipLabel` and `restartLabel` for one-off wording.
  - Intervals, percentages and counts go through `Intl`, so `locale` alone produces "3 j",
    "3 dias" and the right decimal separator without a translation table in this package.

  Backward compatible: with no provider, components use English and the runtime locale exactly
  as before. An invalid locale degrades to English instead of throwing mid-render.

  The patch bumps on the other packages carry README updates only — no code changes.

## 0.2.0

### Minor Changes

- 79714ff: Review pass over the first release: scheduling correctness fixes, new analytics, and the
  first tests for the localStorage adapter. See CHANGELOG.md for the full list.

  Behaviour changes worth knowing before upgrading:

  - `createScheduler()` (SM-2) now throws — it was silently scheduling every card at a fixed
    one-day interval. Use `createFSRSScheduler()`.
  - FSRS is now the default scheduler in `createStudySession()` and `<SRSProvider>`.
  - Lapsed cards enter a ten-minute relearning ladder instead of disappearing until tomorrow.
  - Due dates anchor to the start of the study day (configurable `dayStartsAtHour`).
  - `maximumIntervalDays` defaults to 365, down from 3650.
  - `<SRSProvider>`'s `schedulerConfig` prop is now `fsrsConfig`.

  Second review pass:

  - The relearning ladder now actually works inside a session — it was inert, because sessions
    build their queue once at construction.
  - `preview()` runs the real scheduling path, so button labels match what grading does.
  - Invalid FSRS config throws instead of silently mixing FSRS-4.5 and FSRS-5 weights.
  - Added `resumeStudySession()`, `applyLoadBalance()`, `session.reclaim()` and
    `awaitingRelearning`.

  Adds the FSRS weight optimiser at `@recall-srs/core/optimizer` — fit the 19 parameters to a
  learner's own review history, with a held-out validation set and an honest recommendation
  about whether the result is worth adopting.
